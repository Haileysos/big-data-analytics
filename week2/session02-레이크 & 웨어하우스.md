# Data Lake vs Data Warehouse  
현대 데이터 아키텍처의 두 가지 핵심 저장소 모델 및 특성 비교  
|          | Data Lake | Data Warehouse |   
|:--------:|:---------:|:--------------:| 
| 스키마 접근 | Schema-on-Read 읽는 시점에서 구조 정의, 저장 시 원본 유지| Schema-on-Write 저장 시점에 엄격한 구조 정의 및 검증 |  
| 데이터 타입 | 모든 데이터(정형, 반정형, 비정형) | 정제된 정형 데이터(Structured) |  
| 비용/성능 | 저비용 스토리지, 대량 저장 유리 | 고비용, 고성능 쿼리 최적화 |  
| 주요 목적 | 데이터 탐색, 실험, 머신러닝 | 비즈니스 인텔리전스, 정기 리포팅 |  
| 유연성/거버넌스 | 높은 유연성, 약한 거버넌스 | 낮은 유연성, 강한 거버넌스 |  

<br>

Data Lake : 무엇을 분석할지 모를 때, 모든 데이터를 저장해 탐색과 실험을 하는데에 적합  
Data Warehouse : 무엇을 분석할지 명확할 때, 신뢰할 수 있는 고품질 데이터를 제공하는 데에 적합  

<br>  

## 핵심 트레이드오프  
저장비용 vs 쿼리속도  
> Lake : Object Storage로 저비용  
> Warehouse : 컴퓨팅+스토리지 결합으로 고속응답 제공  

유연성 vs 거버넌스  
> Lake : 자유로운 탐색 보장 but 품질 관리 어려움   
> Warehouse : 엄격한 품질 보장 but 변경 어려움  

실험 vs 표준화
> Lake : 데이터 사이언티스트의 실험적 분석에 적합  
> Warehouse : 경영진의 의사결정을 위한 표준 지표에 적합
 
<br><br>   

# Lake House  
###### Data Lake의 유연성 + Data Warehouse의 성능  
###### 저렴한 스토리지에 원천 데이터를 저장하면서, 트랜잭션 관리와 고성능 쿼리 기능을 동시에 제공  
<br>  

## Lake House 의 핵심 기술  
ACID 트랜잭션    
> 원자성과 일관성을 보장하여 실패 시 데이터 오염을 방지  
> 다중 사용자의 동시 읽기/쓰기 작업을 안전하게 제어  

Schema Evolution    
> 테이블 구조가 변경되어도 데이터 파이프라인이 중단되지 않도록 유연성을 제공  
> 컬럼 추가 및 타입 변경을 지원  

Time Travel    
> 데이터 변경 이력을 버전별로 관리  
> 과거 특정 시점의 스냅샷을 조회하거나 실수로 삭제된 데이터를 즉시 복구    

<br><br>  

## 데이터 파티셔닝 전략  
###### 레이크하우스라는 개념을 실무에서 써먹기 위한 필수 성능 최적화 기법  
###### 파티셔닝 : 불필요한 파일/폴더를 안 읽게 해주는 최적화    
Range 파티셔닝 - 범위 기반 분할  
> 날짜, 숫자 등 연속적인 값의 범위를 기준으로 데이터를 분할 저장  
> 장점 : 특정 기간/범위 조회 시 해당 파티션만 스캔 (Pruning)  
> 주의 : 특정 범위에 데이터가 몰리는 스큐(Skew) 현상 발생 가능  
 
Hash 파티셔닝 - 해시 함수를 통한 균등 분산    
> 파티션 키에 해시 함수를 적용하여 데이터를 여러 노드에 균등하게 분산    
> 장점: 데이터 쏠림(Skew) 방지 및 병렬 처리 효율 극대화    
> 주의: 범위 검색(Range Query) 시 모든 파티션을 스캔해야 함    

List 파티셔닝 - 비즈니스 로직 
> 국가, 카테고리 등 명시적인 값의 목록을 기준으로 데이터를 분류    
> 장점: 데이터 관리/삭제가 용이하며 비즈니스 로직 반영 유리  
> 주의: 카디널리티가 너무 높거나 낮은 컬럼에는 부적합  

Bucketing (버킷팅) - 조인 최적화     
> 파티션 내 데이터를 고정된 개수의 버킷(파일)으로 해시 분할하여 저장  
> 장점: SMB(Sort-Merge-Bucket) 조인 시 셔플(Shuffle) 제거  
> 주의: 작은 파일(Small Files) 과다 생성 방지를 위해 개수 조절 필요

<br>

## 파티션 키 선택 기준    
- 카디널리티 : 너무 적으면 스큐 발생, 너무 많으면 메타데이터 오버헤드 (적절한 수 유지 해야 함)    
- 쿼리 패턴 : WHERE 절에서 자주 필터링 되는 컬럼을 우선 선택하여 스캔 최소화   
- 데이터 스큐 : 특정 키에 데이터가 몰리지 않고 균등하게 분산될 수 있는 키 선택   
- 라이프사이클 : 데이터 보관 주기 및 삭제 정책 관리가 용이한 시간 기반 키 권장    

주의사항 !    
small files problem : 과도한 파티셔닝은 수만 개의 작은 파일을 생성하여 메타데이터 부하를 증가시키고 쿼리 성능을 저하시킨다.    
권장 파티션 크기 : 128MB ~ 1GB

## Data File Formats Comparison  
###### 파일 포맷: 파일 안에서 불필요한 컬럼을 안 읽게 해주는 최적화    
|  format    | type | Schema | Pros | Cons |      
|:--------:|:---------:|:----:|:---:|:---:|   
| CSV | 행 Row-based | X | 높은 호환성, 사람이 읽기 쉬움, 간단한 구조 | 스키마 없음, 압축 비효율, 파싱 속도 느림 |    
| JSON | 행 Row-based | Partial | 중첩 데이터 표현 가능, 웹 친화적, 자기 서술적 | 저장공간 낭비(키 중복), 파싱 비용 높음 |    
| Avro | 행 Row-based | O | 스키마 진화 완벽 지원, 빠른 직렬화, Kafka 표준 | 데이터 확인에 스키마 필수, 컬럼 단위 검색 비효율 |    
| Parquet | 열 Columnar | O | 높은 압축률, 컬럼 스캔 최적화, Spark 생태계 표준 | 쓰기 오버헤드 큼, 전체 레코드 조회 시 느림 |    
| ORC | 열 Columnar | O | Hive/Presto 최적화, 인덱싱/통계 정보 우수 | Spark환경에서는 Parquet보다 덜 효율적일 수 있음 |   

## 최적화 전략  
Row vs Columnar 
> Row : 쓰기 작업, 전체 레코드 조회, 트랜잭션 처리에 유리
> Column : 분석 쿼리, 집계, 특정 컬럼 조회에 유리

Compression
> Snappy : 매우 빠름, 압축률 낮음
