# 분산 시스템 Distributed Systems 의 4가지 핵심 메커니즘   
1. 데이터 파티셔닝 (Partitioning) [scale-out]   
   > 단일 노드 용량을 초과하는 대규모 데이터를 작게 쪼개어 여러 노드에 분산 저장한다.   
   > 이를 통해 물리적 저장 한계를 극복하고 수평적 확장을 가능하게 한다.  
2. 데이터 복제 (Replication) [fault tolerance]   
   > 장애 대비를 위해 동일한 데이터를 여러 노드(기본3개)에 중복 저장한다.   
   > 특정 노드가 고장나더라도 다른 노드의 복제본을 통해 데이터 유실없이 서비스를 지속한다.   
3. 병렬 처리 (Parallel Processing) [performance]   
   > 분할된 데이터 블록을 각 노드가 동시에 처리한다.   
   > 순차 처리 대비 전체 작업 시간을 노드 수에 비례해 획기적으로 단축시킨다.   
4. 조정 & 동기화 (Coordination) [Consistency]   
   > 마스터 노드가 전체 작업 할당, 진행 상황 추적, 장애 노드 감지, 결과 통합을 중앙에서 제어하여 분산 환경의 일관성을 유지한다.   

<br>  

## 왜 분산 시스템인가?  
###### 단일 서버의 물리적 한계를 넘어선 수평적 확장(Scale-out) 전략  
수직적 확장 Scale-Up  
* 물리적 한계 : CPU 속도, 메모리 용량 등 하드웨어 발전 속도의 한계가 존재  
* 비용 비효율 : 최고 사양 서버 비용은 성능 대비 기하급수적으로 증가  
* 단일 장애점 : 서버 1대 장애 시 전체 서비스 중단 위험  

수평적 확장 Scale-Out  
* 선형적 확장성 : 필요한 만큼 저가 서버를 추가하여 성능 증대  
* 비용 효율성 : 가성비 좋은 범용 장비 사용으로 TCO 절감  
* 장애 허용성 : 일부 노드 장애에도 서비스 지속 가능

` [물리적 한계] 슈퍼컴퓨터 1대(Scale-Up)가 매일 쏟아지는 수 PB의 데이터를 혼자 읽고 쓰는 것은 물리적으로 불가능 (CPU와 메모리 속도가 데이터를 따라가지 못하기 때문)   
[극복] 최고 사양 컴퓨터를 포기하고, 보통 사양의 저가 서버 1,000대 이상을 옆으로 길게 연결(Scale-Out). 데이터를 1,000개의 조각으로 쪼개어 1,000대의 컴퓨터가 동시에 일하게 만듦   
[비용 효율성] 만약 초고성능 서버 1대로 해결하려 했다면, 비용이 기하급수적으로 듦. 범용 장비 1,000대를 연결하는 것이 비용 면에서 훨씬 저렴하고 효율적`  

` [단일 장애점] 만약 데이터가 단일 서버 1대에만 저장되어 있다면, 그 서버의 전원 공급 장치가 고장 나거나 불이 나는 순간 전 세계 Facebook 서비스는 그 즉시 마비  
[극복] HDFS 도입. 이 기술은 데이터를 여러 컴퓨터에 나누어 저장하면서, 동시에 똑같은 복사본을 다른 컴퓨터들에도 자동으로 만들어 둠  
[장애 허용성] 덕분에 컴퓨터 몇 대가 갑자기 고장 나서 꺼지더라도, 복사본이 있는 다른 컴퓨터가 즉시 업무를 이어받아 서비스가 끊기지 않고 지속됨    
+  
[물리적 한계] 수억 명의 데이터 속에서 가장 인기 있는 게시물을 찾으려면 컴퓨터 한 대로는 몇 날 며칠이 걸림  
[극복] MapReduce 도입. 기술은  마스터가 수억 개의 데이터를 잘게 쪼개어 수많은 워커 노드에 분배하고(Map), 각자 계산해 온 결과를 다시 예쁘게 하나로 합치는(Reduce) 방식  
[선형적 확장성] 사용자가 늘어나서 데이터가 2배로 많아지면? 서버만 2배로 더 사서 옆에 붙이면  그만입니다. ` 

💡요약                                
Google : 아무리 성능 좋은 단일 서버라도 물리적 한계와 비용 비효율 때문에 수 PB의 데이터를 감당할 수 없음을 보여주는 예시이다.   
Facebook : HDFS와 MapReduce라는 분산 시스템을 통해 서버 한 대가 죽어도 서비스가 멈추지 않고(장애 허용성), 서버를 늘리는 만큼 성능이 똑같이 강력해지는(선형적 확장성) 장점을 극대화한 예시이다.

## HDFS 핵심 특징  
1. 블록 기반 저장 (Block Storage)  
   > 파일을 고정 크기(128/256MB)로 분할해 노드에 균등 분산 저장 병렬 처리의 기본 단위가 됨  
2. 복제 정책 (Replication Policy)  
   > 데이터 유실 방지를 위해 기본 3개 복제본 유지. NameNode가 장애를 자동 감지하고 복구 수행  
3. 랙 인지 (Rack Awareness)  
   > 물리적 Rack 구조를 고려해 복제본 배치. 전원/스위치 장애 시에도 데이터 보호 및 트래픽 최적화  
4. WORM (Write-Once-Read-Many)  
   > 한 번 쓰여진 데이터는 수정 불가. 데이터 일관성 단순화 및 높은 처리량 보장

` '3. 랙 인지 (Rack Awareness)'라는 기술이 실제로 작동하는 모습
"전원선이 통째로 뽑히는 장애가 나더라도 데이터가 유실되지 않도록, 3개의 복사본을 랙(선반) 구조를 고려해서 전략적으로 나누어 담는 모습"을 시각 자료로 증명하고 있는 것입니다.
+
노드 (Node): 그냥 컴퓨터 1대라고 생각하시면 됩니다. (그림의 Node 1 ~ 5)
랙 (Rack): 컴퓨터 수십 대를 꽂아놓은 대형 선반(랙 캐비닛)입니다. (그림의 Rack 1, Rack 2)
중요 포인트: 같은 랙에 꽂힌 컴퓨터들은 전원선과 네트워크 스위치를 공유합니다. 즉, 누군가 발로 차서 Rack 2의 전원선이 뽑히면 Node 4와 Node 5가 동시에 꺼집니다.
+
🔍HDFS는 컴퓨터가 고장 날 것을 대비해 데이터를 3개 복사(Replication Factor = 3)한다고 했습니다. 그런데 이 3개를 아무렇게나 저장하면 큰일 납니다. 만약 복사본 3개를 전부 Rack 2에 몰아서 저장(Node 4에 한 개, Node 5에 두 개)해 놨는데, Rack 2의 전원이 통째로 나가면 어떻게 될까요? 복사본을 3개나 만들었음에도 데이터가 전부 증발합니다. HDFS는 이런 대참사를 막기 위해 '배치 규칙'을 사용합니다. 
그림의 파란 네모(■)가 데이터 복사본입니다. 
사본 1 로컬 노드 (Rack 1의 Node 1 ■) : 내가 현재 작업 중인 컴퓨터(Node 1)에 첫 번째 복사본을 바로 저장합니다. 가장 빠릅니다.
사본 2 다른 랙의 노드 (Rack 2의 Node 4 ■) : Rack 1이 통째로 불타버릴 때를 대비해서, 아예 물리적으로 떨어진 다른 선반인 Rack 2의 컴퓨터에 두 번째 복사본을 보냅니다.
사본 3 사본 2와 같은 랙의 다른 노드 (Rack 2의 Node 5 ■) : 세 번째 복사본은 사본 2가 있는 Rack 2 안에서 다른 컴퓨터(Node 5)에 저장합니다. 랙 간에 데이터를 전송하는 것은 네트워크 비용이 많이 들기 때문에, 이미 데이터가 건너간 Rack 2 내부에서 해결하여 네트워크 트래픽을 최적화하는 것입니다.`
